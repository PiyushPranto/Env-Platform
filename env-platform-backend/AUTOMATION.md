# Model-output update automation

This document explains exactly what the automation in this repo does today,
what is real vs. still missing, and what you need to add for each model
before it stops being "skipped."

## What this automation actually is

Every 3 days (and any time you trigger it manually), a GitHub Actions
workflow (`.github/workflows/update-model-outputs.yml`) runs
`scripts/update_model_outputs.py` on GitHub's own servers — **not** on
Vercel. That script:

1. For each model (heat, flood, deforestation), looks for a matching file
   `scripts/models/<model>_export.py`.
2. If that file doesn't exist, the model is **skipped** — logged plainly,
   not treated as an error, and nothing in `api/data/` changes.
3. If it exists, its `generate(staging_dir)` function is called. It should
   run your real model/notebook code and write real output files into a
   temporary staging folder.
4. Every staged file is validated (`scripts/validators.py`) against the
   exact fields `api/index.py` already expects. Only if **every** file for
   that model passes validation are the files copied into `api/data/`,
   replacing the old ones.
5. If the model code raises an error, or any output file fails validation,
   that model is logged as **failed** and the previous, valid files in
   `api/data/` are left completely untouched. The dashboard keeps serving
   the last good data instead of breaking.
6. `api/data/refresh_status.json` is rewritten every run with the outcome
   per model, and a new endpoint, `GET /model/refresh-status`, serves it.
7. GitHub Actions commits and pushes `api/data/` **only if something
   actually changed**, so Vercel's normal git-push deploy picks it up —
   nothing about your Vercel project settings needs to change.

**No part of this fabricates data.** With zero `scripts/models/*_export.py`
files present (the state this repo ships in), every run of the automation
will report all three models as `skipped` and make zero changes to
`api/data/`. That is the correct, honest behavior — not a bug to fix.
You can see this yourself: the included `api/data/refresh_status.json`
was generated by actually running the script in this state.

## What's real right now vs. what's missing, per model

### Heat
**Missing entirely.** There is no Heat model code anywhere in this
project — no notebook, no script. `api/data/heat_risk.json`,
`heat_trend.json` and `heat_grid.json` are hand-authored placeholders.
To make this real: build the Random Forest UHI + composite risk score
model referenced in `api/index.py`'s docstrings, then create
`scripts/models/heat_export.py` (copy `scripts/models/_template_export.py`)
whose `generate()` runs it and writes `heat_risk.json`, `heat_trend.json`,
`heat_grid.json`, `heat_hotspots.geojson` with the same field names the
backend already reads.

### Flood
**Two separate efforts exist; neither is wired into the automation yet,
and you need to decide which one this runner targets** (see the long
comment at the top of `scripts/runners/flood.py` for the full context):

- The Dhaka-only rule-based composite score currently served by
  `/flood/*` — a one-time analysis over a fixed window, not really
  something a 3-day cron regenerates unless you rebuild it on a rolling
  window.
- The newer nationwide (64-district) trained Random Forest classifier
  (`build_bangladesh_flood_model.py` / `bangladesh_flood_model_colab.ipynb`)
  with a real `predict_today()` stub and real evaluation metrics
  (precision 0.12, recall 0.83, F1 0.21, ROC-AUC 0.91 on real 2018 ground
  truth) — a much better automation candidate, but its GEE exports
  currently go to a personal Google Drive (not reachable headlessly), and
  its output shape doesn't yet match `flood_grid.json` /
  `flood_summary.json` / etc.

Either way, create `scripts/models/flood_export.py` whose `generate()`
produces the four existing flood filenames with the existing field names.
Which underlying model feeds it is your call — the automation plumbing
doesn't care.

### Deforestation
**Real methodology and code exist** (`deforestation_model.ipynb`,
`deforestation-model-summary.md`, `deforestation-api-contract.md`), but as
stored in this project the notebook has **never actually been run** —
every cell has `execution_count: null` and empty outputs. Two things to
resolve before this can run headlessly every 3 days:

1. **GEE export path.** The notebook's feature stacks are exported via the
   interactive GEE Code Editor to a personal Google Drive. That can't run
   unattended. You'd need to rewrite the export using the Python
   `earthengine-api` with a service account (stored as a GitHub Actions
   secret), exporting to somewhere this workflow can read headlessly (e.g.
   Google Cloud Storage) instead of Drive.
2. **Cadence mismatch, flagged honestly.** This model is built on *annual*
   seasonal MODIS NDVI composites. Running it every 3 days will, most of
   the time, reprocess byte-identical source data and produce an unchanged
   result — it just won't have new source imagery most weeks. The
   automation still follows your requested 3-day schedule (nothing here
   silently overrides that), but if you'd rather this specific model run
   less often, that's a small, isolated change (a second `schedule:` entry
   in the workflow) — not something the runner itself needs to know about.

Once you have headless-capable export code, create
`scripts/models/deforestation_export.py` the same way as the others.

## The one honest limitation of the 3-day cron schedule

GitHub Actions cron (`0 2 */3 * *`) fires on day-of-month 1, 4, 7, ...,
31, then wraps back to 1. Depending on the month, the gap between the last
scheduled day and the 1st of the next month can be 1-2 days instead of
exactly 3 — a real quirk of cron's day-of-month field, not something this
setup can silently fix. If you need a mathematically exact rolling 3-day
interval regardless of month boundaries, ask and a small "skip if the last
successful run was under 3 days ago" guard can be added inside the script
itself (checked against `refresh_status.json`) — deliberately left out for
now to keep the initial version simple, per your priority on simplicity.

## What you do NOT need to change

- **Vercel deployment configuration** — nothing about it changes. It keeps
  deploying `api/index.py` exactly as before; the only difference is
  `api/data/` files may now also get updated by a git push coming from the
  Actions bot instead of from you.
- **The frontend** — zero changes. Every endpoint it already calls returns
  the exact same shapes; the automation only ever replaces file contents,
  never field names or endpoint paths.
- **`requirements.txt`** (the backend's own dependency file) — untouched.
  Heavy ML/geospatial dependencies for your real model code go in the
  separate `scripts/requirements-automation.txt`, which is installed only
  inside the GitHub Actions runner, never inside the Vercel function.

## How to add a real model (step by step)

1. Copy `scripts/models/_template_export.py` to
   `scripts/models/<heat|flood|deforestation>_export.py`.
2. Port your real Colab code into its `generate(staging_dir)` function.
   Write your real output files into `staging_dir` using the exact
   filenames listed in `scripts/runners/<model>.py`'s `OUTPUT_FILES`.
3. Add whatever your real code needs to
   `scripts/requirements-automation.txt`.
4. If it needs credentials (e.g. a GEE service account key), add them as a
   GitHub Actions repository secret and reference
   `${{ secrets.YOUR_SECRET_NAME }}` in the workflow's `env:` — ask if you
   want this wired up once you have the actual credential.
5. Test locally first: `python scripts/models/<model>_export.py` (the
   template includes a `__main__` block for this), then
   `python scripts/update_model_outputs.py` to confirm it validates and
   promotes correctly, exactly as demonstrated in this delivery.
6. Commit and push. The next scheduled run (or a manual
   "Run workflow" click in the Actions tab) will pick it up automatically
   — no further code changes needed.

## What was manually tested before delivery

Since this sandbox has no access to your real GitHub repo or Vercel
project, everything below was verified in an isolated local copy rather
than in your actual deployment:

- Running the orchestrator with zero `scripts/models/*_export.py` files
  present: all three models correctly reported `skipped`, zero changes to
  any `api/data/` file, `refresh_status.json` written correctly.
- Adding a fake, *valid* `heat_export.py`: its output was validated and
  correctly promoted into `api/data/heat_risk.json` etc.
- Adding a fake, *failing* `flood_export.py` (raises an exception) at the
  same time: `flood_grid.json` was byte-for-byte unchanged afterward — a
  failure in one model never touches another model's files, and never
  touches its own previous valid output.
- Adding a fake heat export that produces *invalid* output (missing
  required fields): rejected by the validator, previous valid
  `heat_risk.json` left completely untouched.
- `GET /model/refresh-status` and all 11 pre-existing endpoints tested via
  FastAPI's test client after the `api/index.py` edit — all still return
  200 with unchanged shapes.
